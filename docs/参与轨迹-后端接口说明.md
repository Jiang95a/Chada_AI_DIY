# 参与轨迹（Traces）后端接口说明

> 对应前端提交 `f4fba7e feat(参与端): 动态参与与个人轨迹闭环`。
> 契约来源：`web/src/services/traces.ts` 文件头注释 + `web/src/types/trace.ts` 的 `ParticipantTrace`。
> 状态：**后端与数据库已实现**；`/traces/list` 已接前端，另新增 `/insights/facts` 回看聚合（不调用模型）。

## 1. 结论：前端无需改代码

前端从一开始就按「后端未就绪时静默降级」写的（`web/src/services/traces.ts:14`
`const UNSUPPORTED = new Set([0, 404, 405, 500, 501, 502, 503])`）。
后端上线后，同一个前端会自动从「只存在这台设备」切到跨设备同步，**不需要发版**。

唯一需要前端补的是一个新接口：`GET /traces/list`（见第 4 节），
它目前没有调用方，属于「后端已就绪、等待接线」的状态。

## 2. 已实现接口

全部需要登录（`AuthInterceptor` 的 `PUBLIC_PREFIXES` 不含 `/traces`），未登录返回 401。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/traces?activityId={slug}` | 取本人在该活动的轨迹，无记录时 `data: null` |
| PUT | `/traces/{slug}` | 整条覆盖保存 |
| GET | `/traces/list?limit=50` | 「我的轨迹」跨活动列表（**新增，前端待接**） |
| DELETE | `/traces/{slug}` | 删除，幂等 |
| GET | `/insights/facts?days=30` | 回看数据聚合：活动/表单/轨迹/标签时间线，需登录 |

### 路径参数是 slug，不是 UUID

`web/src/components/public/DynamicParticipation.vue:33`
`const activityId = computed(() => props.slug)` —— 前端传的 `activityId` 是活动的
`public_slug`（如 `activity-ia38wg`）。服务端用 `ProjectMapper.findByPublicSlug` 反查成 UUID 再落库，
回传时仍用 slug。这样活动改 slug 后轨迹不会变成孤儿数据。

### GET 返回 `data: null` 而不是 404

`traces.ts:17` 的 `unwrapTrace` 把 `null` 当「远端没有，用本地的」；
而 404 会命中 `UNSUPPORTED` 被判成「后端不支持」，两条分支的 UI 文案不一样。
所以「没有轨迹」必须是 200 + `data: null`。

### 401 的例外

未登录调 `/traces` 返回 401，前端 `fetchRemoteTrace` 会 catch 后返回 null，同样走降级。
而 `stores/trace.ts:145` 本来就有 `if (!getAccessToken()) return`，未登录根本不会发起请求。

## 3. 关键行为（有测试覆盖）

- **userId 一律取 token**，请求体里的 `userId` 被忽略。前端本地缓存的旧 userId 带上来也不会写错行。
- **整条覆盖，不做字段合并**：前端每次 PUT 的是完整轨迹，服务端若自作聪明合并，
  会出现「前端删掉的标签在服务端复活」。测试断言了「第二次 PUT 后 tags 从 2 条变 1 条」。
- **updatedAt 原样存客户端毫秒时间戳**，不改成服务端时钟。
  `stores/trace.ts:181` 用 `normalized.updatedAt >= base.updatedAt` 判断新旧，
  服务端改写会让时钟偏差导致用户本地改动被判「更旧」而丢失。
- **只有本人能读写**。没有任何接口能看别人的轨迹，组织者也不行——
  轨迹里有「未决问题」「想做出的改变」，比报名答案私密得多。
- **空轨迹不进列表**：`summary` 和 `tags` 都为空的不列出，与前端 `list()`（`stores/trace.ts:268`）同口径，
  否则用户点进活动什么都不做也会留一条空记录。
- **domain 只接受 mental / career**，其他值归一到 mental 而不报错——
  这是前端枚举，写错不该让用户丢掉整条轨迹。表的 CHECK 约束兜的是绕过接口直接改库。

## 4. 前端待接：`GET /traces/list`

`web/src/views/TraceTimelineView.vue:22` 现在是 `items.value = traceStore.list()`，
只读 localStorage（`stores/trace.ts:265`）。**换设备后「我的轨迹」页是空的。**

后端已提供：

```
GET /traces/list?limit=50
→ { "data": [ { "activityId": "...", "activityTitle": "...", "domain": "mental",
                "semester": "2026-秋", "summary": "...", "tagCount": 2, "updatedAt": 1763...} ] }
```

建议接法（最小改动）：在 `stores/trace.ts` 的 `list()` 里，登录态下先拉远端，
把结果合并进返回值（远端优先，本地补缺），失败时保持现有的纯本地行为。
这样 `/trace` 页换设备也能看到历史。

注意列表项**不含完整 payload**（没有 tags 数组明细、没有 notes），
只有 `tagCount`。这是刻意的：列表页只需要摘要，拉全量会让一次请求带几十条轨迹的完整内容。

## 5. 数据库

`docs/sql/011_participant_traces.sql`，已在本地库执行，`health.database.tables` 从 16 变 17。

```sql
CREATE TABLE participant_traces (
  user_id       CHAR(36)     NOT NULL,
  project_id    CHAR(36)     NOT NULL,   -- 由 slug 反查得到，不是 slug
  domain        VARCHAR(16)  NOT NULL DEFAULT 'mental',
  semester      VARCHAR(32)  NOT NULL DEFAULT '',
  summary       VARCHAR(500) NOT NULL DEFAULT '',  -- 冗余自 payload.summary，列表页用
  payload       JSON         NOT NULL,   -- 完整 ParticipantTrace
  updated_at_ms BIGINT       NOT NULL,   -- 前端毫秒时间戳，原样保存
  ...
  PRIMARY KEY (user_id, project_id),
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
  FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE
);
```

**为什么整条存 JSON 不拆表**：轨迹结构还在演进（一期前端关键词规则引擎，三期换 agent），
拆成 tags / notes / session_context 三张表会让每次加字段都要迁移；
而读取永远是把整条取出来，没有按标签检索的需求。等真需要按标签统计时再拆。
`summary` 冗余一列是为了列表页不必为每条记录解析 JSON。

**主键是 (user_id, project_id)** 而不是自增 id：这张表没有任何地方需要「按 id 找一条轨迹」。

## 8. 回看数据聚合 `/insights/facts`

这是给后续「回看」用的数据底稿，**不调用模型、不做诊断、不返回表单答案**。

```http
GET /api/v1/insights/facts?days=30
Authorization: Bearer <token>
```

返回：

```json
{

  "periodEnd": "2026-11-17",
  "generatedAt": "2026-11-17T12:00:00.000Z",
  "activityCount": 4,
  "formCount": 6,
  "traceCount": 4,
  "eventCount": 18,
  "activities": [
    {
      "activityId": "photo-club-2026",
      "activityTitle": "摄影社招新",
      "domain": "mental",
      "lastAt": 1763000000000,
      "eventCount": 3,
      "tags": ["压力", "人际"],
      "summary": "今天说出来了"
    }
  ],
  "events": [
    {
      "source": "activity",
      "activityId": "photo-club-2026",

      "at": 1763000000000,
      "kind": "input",
      "tags": ["人际"],
      "summary": "今天说出来了",
      "change": null
    }
  ],
  "forms": [
    {
      "activityId": "photo-club-2026",
      "activityTitle": "摄影社招新",
      "submittedAt": "2026-11-16T12:00:00.000Z",
      "status": "valid"
    }
  ],
  "tagCounts": { "压力": 2, "人际": 1 }
}
```

约定：

- `activityCount` 是「轨迹 ∪ 有效表单」去重后的活动数，由 SQL 算，不交给模型
- 匿名表单没有 `user_id`，不计入个人活动数，也不返回答案
- `forms` 只有「哪天提交过哪场活动」，没有 `answers`
- `events` 来自 `trace.payload.history`；老数据没有 history 时，合成一个 `input` 点
- 工具页记录还在本机，由前端 `services/insights.ts` 合并成 `source: "tool"` 事件，
  并用 `toolRecordCount` 单独计数；不混进活动数
- `days` 默认 30，最大 365；未登录返回 401

已补的后端字段：

- `ParticipantTraceDto.history`：跨设备保留完整个时间线
- `SaveTraceRequest.history`：整条覆盖保存时一起写入 `payload.history`
- `ConsentResult.consentRequired`：公开页可以据此决定是否必须勾选参与说明
